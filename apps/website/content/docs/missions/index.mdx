title: Missions and agents
description: Create a mission, give its key to an agent with the kit the instance prints, and what the agent reads when a call is refused.

A mission is created by a person, in the interface or through a connected app, and handed to an agent as a key plus a kit: the MCP client configuration, the instructions for the agent and a command to check it.

## Create a mission

In the interface: Missions → New mission, on one screen.

1. **Name it** after the task ("Ship the billing page").
2. **Include accounts** and select the resources the task needs, not all of them. You can include an account you own or one you were given access to; one account per service.
3. **Tick macro-actions** per account ("Read", "Propose", "Ship"…) and set each to a trust level, **Careful**, **Trusting** or **Autonomous**: each row says how many permissions run freely, ask first or are left out here. **Advanced** opens every permission with its limit per period, its rate per minute, and "runs freely" or "ask me first".
   For your own agents or a break-glass mission, **"Everything I hold on this account"** writes out every permission you may allow on that account that the selected resources can reach, the uncategorized writes included: each runs freely, at the service's rate ceiling, with a generous daily limit. Before you choose it, it says how many permissions that is, the one hardest to repair and which of those that cannot be repaired would run freely. The mission still stores that explicit list: if you are given more later, the mission does not grow.
4. **Choose the period and the expiry**: once, or limits reloaded every day; an end date, or none (a forgotten mission without an end keeps its keys valid).
5. **Create mission**: the form lists every permission with its limit before anything exists.

A mission can only hold what you may allow yourself: the permissions of the accounts you own, or what an access you were given allows.

## Give the key to the agent

The key is shown once, followed by the kit:

- **The environment variable**, `export VAUBAAN_MISSION_TOKEN='...'`, to set where the agent runs.
- **The MCP client configuration**, which reads the key from that variable, never the secret itself:

```json
{
  "mcpServers": {
    "vaubaan": {
      "type": "http",
      "url": "https://your-domain/mcp",
      "headers": { "Authorization": "Bearer ${VAUBAAN_MISSION_TOKEN}" }
    }
  }
}
```

- **Instructions for the agent**, in Markdown: whose key it is, the accounts and resources it may touch, each permission with its limits, what each refusal means and what to do, the management door's address.
- **The git configuration**, when the mission holds repositories: see [git remote](/docs/missions/git-remote).
- **A check**, a `curl` that lists the tools the key opens.

Configuring the main clients: [MCP clients](/docs/missions/mcp-clients).

## Teammates and keys

The creator can add teammates; each generates their own key, shown to them alone, and every call is recorded under the holder of the key that made it. The limits are one for the whole mission, never multiplied by its keys. A machine key (for a CI runner) is a key with a name instead of a person. Removing a teammate refuses their key at once; the others keep working.

## When a call is refused

The gateway answers with a code and what to do; it never holds a call waiting.

| Code                      | Meaning                                                                 | What happens next                                                                                        |
| ------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `risk-not-accepted`       | the call needs a permission the mission does not hold (`missing_risks`) | the creator may change the mission; the agent does not work around it                                    |
| `budget-exhausted`        | a limit is reached for this period                                      | the answer carries a `claim_url`; the creator gives more or resets it under "Waiting for you"            |
| `approval-required`       | the permission asks first                                               | the answer carries an `approval_url`; once the creator approves, the agent replays exactly the same call |
| `resource-not-in-mission` | the resource is not selected in the mission                             | the creator may add it                                                                                   |

The kit's instructions list every code the instance can return. Stopping a mission or removing an access stops every call at once.

## The mission page

Missions → a mission, in the order you need it: its state and the header's actions (**Edit mission**, the setup kit, and behind "···" stop, duplicate, replace your key); what waits for your answer on it; what it holds, card by card, with how much of each limit the period has used; the people and keys, with what each key did; and its activity. The creator and the teammates read it; each sees only the acts that are theirs (a teammate generates, replaces and revokes their own key; the creator adds people, makes machine keys, edits and stops the mission).

## Resources found later

When you select the resources of an account, a card can also take **the resources found later in the same environment** ("+ future repositories"): a resource that appears on the account afterwards with that environment label — discovered, or relabelled into it — joins the mission, unless another card of the mission already holds it. Without it, the mission reaches the resources it lists and no other. A resource the mission creates itself through the gateway joins it either way. The owner labels resources on the [account's page](/docs/accounts#environment-labels).

## Edit a mission

The creator, and only the creator, opens **Edit mission** on the mission page: the creation form, filled in with the mission. Everything can change but the period: accounts, resources, macro-actions and trust levels, single permissions, limits, the end date. Review what is added and removed, then **Save changes**. Every person and key on the mission gets the change at once; keys, history and what the period used stay, and removing then adding a permission does not reset its use. A stopped mission is never edited: duplicate it instead.

An agent that receives `risk-not-accepted` may ask for the missing permission through `vaubaan__request_permission`, with the refusal's `refusal_id` and a reason. Nothing reaches you until the agent asks. Under **Waiting for you**, read what it says, add the permissions, or refuse. Granting changes the mission; the agent still retries its call.

## The activity of a mission

The mission page's **Activity** leads to its own record: what waits for an answer, who called in the current period — per key holder and per agent label —, the timeline of its calls and changes, then what each permission used and the counters of the earlier periods. A key holder is whose key made the call; an agent label is what the agent said about itself. Neither is a limit: a mission has one set of limits, however many keys or agents. The whole record of the instance is [Activity](/docs/interface#activity).
