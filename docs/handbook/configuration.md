# Instance configuration, crypto and composition root — handbook

How the process starts from configuration alone and wires its modules. Spec:
[vaubaan-gateway](../spec/vaubaan-gateway.md) §4.3, §6.

## Start here

- [`config/sources.ts`](../../apps/gateway/src/server/config/sources.ts) — `KEYS`, the table below.
- [`compose/root.ts`](../../apps/gateway/src/server/compose/root.ts) — wiring order, closers, boot checks.
- [`compose/boot-config.ts`](../../apps/gateway/src/server/compose/boot-config.ts) — key generation, setup mode.
- [`src/proxy.ts`](../../apps/gateway/src/proxy.ts) — security headers, CSP nonce, setup redirect.

## Invariants

- `server/` never imports `next`; nothing outside `server/config` reads a
  secret from `process.env`, which `loadProcessConfig()` scrubs once loaded.
- Nothing in `next.config.ts` reads instance configuration; `commit` comes
  from `build-commit.txt` (`git archive`) or HEAD, never a variable.
- **Self resources** (`RAILWAY_PROJECT_ID`, `FLY_APP_NAME`, `self_resources`)
  are reached by no mission: every reader of mission resources calls
  `isSelfResource`.
- Sealed columns are listed once (`store.sealedBlobs`): the boot probe and
  `reseal` see only those. The connection id is the AEAD associated data.
- Logs carry an error's class and frames, never its message.

## Traps

- **The file wins over the environment**, key by key, silently: the example
  YAML ships with every key commented out.
- A value still holding `${...}` after resolution (Compose's
  `${VAR:-default}`) is an error, never a literal secret.
- `client_ip_header` is safe only behind an edge that overwrites it, else a
  client picks the address it is limited and audited under: send a forged
  value from outside and check the recorded one. With `NODE_ENV=production`
  (the image) and neither key, the boot refuses (exit 78) unless
  `accept_shared_address_windows`: every address window is then shared by all
  callers (boot `warn`). The demo and the tests load their own environment,
  without `NODE_ENV`, and are never refused. Trust one proxy address (the
  compose file: Caddy's `172.30.253.2`), never a Docker pool.
- A boot failure after the store opened runs the closers in reverse: register
  any new timer or handle with them, or a retry holds a second SQLite handle.
- `compress: false` (gzip would buffer streamed MCP answers); the proxy skips
  `/git/` for the same reason; the CSP has no `form-action` (posts that end at
  a provider); a file read at run time goes in `outputFileTracingIncludes`.
- Node's major moves in one PR (Dockerfile `FROM`, workflows, `engines`,
  `@types/node`); the glibc `bookworm-slim` base is pinned by digest.
- **OAuth brokers**: a brokered connection names the block it was made with;
  renaming a block strands its connections. `attestation: none` skips the
  check for one broker, it never adds a version to the allowlist shipped with
  the release (`connections/broker-measurements.json`, empty until a broker is
  released); an attested broker is reached at a root URL with a port, over its
  own TLS key ([oauth-broker-contract](oauth-broker-contract.md)). **Instance name** set in the
  configuration makes the stored one ignored.

## Procedures

### Master key generated at the first start

- A missing key file on a store with content is exit 78, never a new key: put
  the file back.
- Compose generates it on `/keys` (volume `gateway-key`), apart from the store;
  a key file on the store's mount is one boot `warn`
  (`compose/key-placement.ts`, `/proc/self/mountinfo`), silenced by
  `encryption.accept_key_beside_store`. Moving an older instance's
  `/data/master.key`: `deploy/README.md`.

### Setup mode: the setup receives the key for a restore

- New host without a shell: `restore.from` + `restore.sha256`, empty volume,
  no key file; upload token and key file at `/admin/bootstrap`.
- Wrong tokens are counted in `<key directory>/setup-misses` (`setup/misses.ts`),
  across restarts; at 50 the page refuses until that file is deleted.

### Rotating the master key

1. Back up ([store](store.md)); keep the old key while a backup sealed with it
   is kept.
2. `npm run gen-master-key`; set `VAUBAAN_MASTER_KEY`, raise
   `VAUBAAN_MASTER_KEY_VERSION`, set `VAUBAAN_MASTER_KEY_PREVIOUS=<v>=<old>`;
   deploy the three together.
3. In the container (`vaubaan-entrypoint` first where it runs as root):
   `node apps/gateway/reseal.mjs` (dry run), `--apply`, dry run again. Safe
   beside the running server; `changed` means run again.
4. Only after a clean run, remove `VAUBAAN_MASTER_KEY_PREVIOUS`.

## Debug

- **Exit 78** → configuration; stderr names the key and its variable.
- **"stored secrets do not open with the configured master keys"** → version
  not raised, or `VAUBAAN_MASTER_KEY_PREVIOUS` missing.
