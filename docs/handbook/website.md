# The public site — handbook

How `apps/website` builds vaubaan.com from the repository at build time, and reads plugin health when a page is served. Spec: [website](../spec/website.md) §2; ADR [website-nextjs-on-vercel](../decisions/website-nextjs-on-vercel.md); the collector sharing the app: [telemetry](telemetry.md).

## Start here

- [`scripts/generate.ts`](../../apps/website/scripts/generate.ts) — the build-time generator; `npm run build`, `dev` and `type-check` all run it first. It reads no network.
- [`src/content/build-site.ts`](../../apps/website/src/content/build-site.ts) — `buildSite()`, every page and public file from what `src/content/` reads in the repository.
- [`src/site/live.ts`](../../apps/website/src/site/live.ts) — what is rendered at request time: the pages under `/plugins`, every Markdown twin (`app/twins`), `plugins.json` and `llms-full.txt`, with the collector read and cached an hour.
- [`packages/plugin-page/`](../../packages/plugin-page/) — **the plugin page is shared with the gateway's Reference** ([ADR](../decisions/service-page-is-one-shared-package.md)): `info.ts` (`pluginInfo(plugin, context)`, the data contract), `examples.ts` (the classified examples), `load.ts` (`discoverPluginDirs`, `importPlugin`), `page-data.ts` — the page data in the Atlas layout, section by section (spec §2.3, 1–8): `ledeOf`/`countsOf` (header), `modelOf` (nested `ModelNode`s, `summaryParts`, `isResourceEntity`, `CARDINALITY_WORDS`, `ENVIRONMENT_RULES`), `macroActionsTitle`, `mapOf` (chips per row and macro-action, `toggleEnvsOf`, `cellWords`, sums, notes), `callsOf`, `anythingElseSentence`, `toolsIntro`, `retiredOf`, the connect guide (`connectKindBadge`/`connectKindCode`, `brokerAdminSentences`, `connectSentences`, `grantsHeading`, `ALTERNATIVES_LEGEND`, `PATH_SEPARATOR`, `screenshotCredits`, `expiryText`), `sectionNumbers` —, `ServicePage.tsx` (the HTML) and `marks.tsx` (mono, the one-word gate, the (i) tooltip, the service mark), styled by `plugin-page.css`. What the site hands in is in [`components/plugin/PluginPage.tsx`](../../apps/website/src/components/plugin/PluginPage.tsx) (`sourceHref` = GitHub, the crumbs, the gateways on the counts line, the health and links sections, the foot) and [`content/plugins.ts`](../../apps/website/src/content/plugins.ts) (`loadPlugins`, `sitePluginInfo`: the folder, the package, the examples' file, `connectFigureSrc`); `pluginPageMarkdown` (`plugin-pages.ts`) writes the twin from the same page data, in the same order; `connectGuidePath` and `siteDir` are `outputs.ts`'s.
- [`src/content/references.ts`](../../apps/website/src/content/references.ts) — the generated references under `/docs/reference/` (spec §2.2): refusals (codes from `@vaubaan/shared`, fields and example hints from `refuse` of `@vaubaan/gateway-core`, "what happened" and "what the agent does" from the tables of §5 of the agent bootstrap, "what you do" from `PERSON_NEXT`), rows by trust level (policy engine), words (the shared words of the gateway spec §0 and its interface-words table, §0 bis) and the agent bootstrap itself (`for-agents`). Each reader throws when its source changes shape.
- [`src/proxy.ts`](../../apps/website/src/proxy.ts) — the collector host gate and the rewrite of `.md` addresses and `Accept: text/markdown` to the twins route.
- [`src/app/globals.css`](../../apps/website/src/app/globals.css) — the one stylesheet: Tailwind v4 (`postcss.config.mjs`), the shared tokens of [`@vaubaan/design-tokens`](design-tokens.md), the `.prose` rules of rendered Markdown, the `--pp-*` mapping of the plugin page. Components style themselves with utilities; shadcn/ui parts are copied into `src/components/ui/` and owned (only what the site uses: `Button`), with `cn` in `src/lib/utils.ts` ([ADR](../decisions/design-system-on-shadcn-shared-by-the-app-and-the-site.md)).
- **The landing and the product pages** (spec §2.1, §2.1 bis): their words are data, written once, rendered by the page and written as its Markdown twin by the generator — [`src/site/landing.ts`](../../apps/website/src/site/landing.ts) (the promise, the defining sentence, the hero's call log, the steps built or planned, protects / does not, the questions) and [`src/site/product-pages.ts`](../../apps/website/src/site/product-pages.ts) (`/how-it-works`, `/teams`, `/try`, `/write-a-plugin`: sections of Markdown, a drawing, a status, a link; a text is one string or `{ dev, consultant }`). The views are [`components/site/`](../../apps/website/src/components/site/): `Landing.tsx` (`/` and `/consultants`, which differ only by `initial`), `ProductPageView.tsx`, `Project.tsx` (the project switch, `ForProject`, `VariantText`, `Drawing`). The navigation and the footer are `NAV` and `FOOTER` in [`components/Shell.tsx`](../../apps/website/src/components/Shell.tsx).
- **The drawings** — [`drawings/`](../../apps/website/drawings/): `gen.py` (the scenes, the short names of the permissions in `SHORT`) and `prims.py` (the palette, light and dark, value for value the tokens; the shapes) write `drawings/svg/<name>[-consultant]-<light|dark>.svg` and `drawings.json` (title, text alternative, size) from `facts.json`, which [`scripts/drawing-facts.ts`](../../apps/website/scripts/drawing-facts.ts) writes from the catalogs (`src/content/drawing-facts.ts`). The SVGs are committed: the site's build runs no Python; `buildSite` copies them to `public/drawings/` (`drawingAssets`, `src/site/drawings.ts`) and the README shows two of them from their committed path.
- [`content/docs/`](../../apps/website/content/docs/) — the hand-written docs; `meta.json` orders the sidebar. `interface.mdx`, `accounts.mdx` and `administration.mdx` explain the gateway's pages one heading each: the (i) of each page header links there (`DOC_PAGES` in the gateway's `vocabulary.ts`). `concepts/` holds the explanations (`index.mdx` is `/docs/concepts`, `permissions.mdx`, `how-a-call-flows.mdx`); `index.mdx` routes each reader ("pick your path") to existing pages only.

## Invariants

- **The site reads the repository, not a copy.** Plugins are loaded through their `exports["."]` and validated by `definePlugin` and the catalog loader as at gateway boot; the configuration key table, [known-limitations](known-limitations.md), the [threat model](threat-model.md) (`trust.ts`) and the thresholds of `deploy/collector/schema.sql` are parsed from their files. Reshaping one of those docs can break the site: grep `apps/website/src/content/` first.
- **The plugin author's guide (`content/docs/plugins-guide`) speaks of the published kit only** (spec §2.2 bis): `npx @vaubaan/plugin-cli`, the project it makes, the catalog repository; never a path of this repository, so `plugins/` may leave it. Its three references are hand-written and held to the code by `plugins-guide.test.ts`: the command line page carries every line of the CLI's `USAGE` verbatim and one heading per command; the catalog file page lists every value of `RISK_VECTOR_AXES`, and its row × trust level table is `TRUST_LEVEL_GATES` in `GATE_WORDS`, its budget line `TRUST_LEVEL_BUDGET_FACTOR`; every message the errors page quotes is found, around its `…`, in the SDK, the CLI, the scaffold or the gateway. A changed message, command or rule fails there first. The tutorial "Your first plugin" is the flow of `scripts/plugin-kit-smoke.sh`: change one, change the other.
- **A link into the repository lands on a heading that exists.** `site.test.ts` ("links into the repository") checks every `github.com/vaubaan/gateway/blob/main/<file>.md#<anchor>` of every page, and of the gateway's `lib/project-docs.ts`, against the headings of that file, slugged as GitHub does. Deployed instances link `deploy/README.md#pin-a-plugin`: that heading stays, as a pointer to the site, even though the procedure moved there.
- **Nothing of the gateway is restated by hand**: rows, reasons, gates and budgets come from `@vaubaan/policy-engine` (`rowOf`, `reasonOf`, `REASON_AXIS` — the fact that moved the gate, tinted —, `TRUST_LEVEL_GATES`, `budgetAtTrustLevel`, `expandAtTrustLevel`, `evaluateCall`, `macroActionsOf` for "Anything else"), and so do the words a person reads of the risk model (`WHY_LABELS`, `WHY_ORDER`, `WHY_VALUES`/`whyValue` — the five facts and the undo word —, `ROW_WORDS` — the rows of the map —, `REASON_WORDS`, `ROW_LABEL`, `TREE_LEGEND`, `gateWordOf`/`GATE_WORDS`, `ALLOW_WORDS`, `TRUST_LEVEL_LABELS`, `TRUST_LEVEL_HINTS`), which the gateway's `lib/vocabulary.ts` re-exports; the client source comes from `isBrokeredSpec` of the plugin SDK — packages, allowed by the ADR; `apps/gateway` stays forbidden. **`sources-agree.test.ts`** holds it: the gateway's vocabulary exports the very values of the policy engine, every fact the site shows is `factsOf()`'s, and `plugins.ts`, `plugin-pages.ts`, `outputs.ts`, `components/plugin/PluginPage.tsx` and the shared package's sources contain none of those words as a literal (`ROW_WORDS` and `REASON_WORDS` included; a reason spelled like a catalog value, `irreversible`, is a protocol name and exempt); beside it, the key page against `KEYS` and the thresholds against the collector README. A word missing from the policy engine is moved there (and re-exported by the gateway when its interface prints it), never written in the site.
- **`PluginInfo` (`@vaubaan/plugin-page/info`) is the data contract of a plugin page** (spec §2.3); `dir`, `packageName` and `examplesSource` are `null` where the app does not know them (the gateway): every shape is plain, serialisable data and `plugins.json` writes it out. `dataModel` is the plugin's own (`touched`: a classified example's slice names the entity), `environment` mirrors the gateway reference's `environmentOf` (`call` when the plugin declares `envOf`, else `resource-label` when the catalog names an environment, else `none`); a way's `steps` are the guide's shared steps and `alternatives` hold each shape's own (`allSteps()` gives both, for the screenshots). A macro-action's entries are in catalog order with retired permissions left out (as the gateway's form); `anythingElse` and `retired` are apart from `macroActions`; `counts.permissions` leaves out the fallback and the retired (GitHub: 17). A quota is per period, written per day on the page (a mission's default period); the per-minute ceiling is a note.
- **Examples are classified at build** (`examples.ts` of the package; the gateway's Reference passes `examples: 'lenient'`, the site fails its build): each sample of `plugin.examples` goes through the plugin's own `classify`, its slices through the policy engine's matcher, and two decisions: `atCareful` — "what a Careful mission does", the gate Careful gives each permission the call touches (`evaluateCall` against an empty mission names them env-qualified, `TRUST_LEVEL_GATES.careful` on the row in that environment) — and `inWorkedMission`, what the worked mission written in `plugins.json` (no longer on the page; the first two macro-actions at Careful, `expandAtTrustLevel` + `evaluateCall`, over the sample's resources) does with it. A tool's `touches` is the union of its examples' permissions. A sample marked `expectDenied` is a test of the refusal: checked, not shown. The site never writes a slice by hand.
- **A plugin page is HTML built from its data, not rendered Markdown** (the other generated pages are): `ServicePage` and `pluginPageMarkdown` read the same `page-data.ts` builders, so a section added to one is added to the other. The map's rows are `MAP_ROWS` (4 → 1) named by `ROW_WORDS` with `ROW_GATE_SENTENCES`; a chip is a permission in one row, an env-qualified permission one chip per row and reason its toggle environments land in (each environment's vector), an environment its `acceptable_in_envs` leaves out a dashed "never on <env>" chip in its own row; the fallback is only in "Anything else". The sums count each permission once. **The page never prints "tier" nor "severity"**: `service-page.test.tsx` (package) and `plugin-page.test.tsx` (site, with the twin) render every plugin and refuse both.
- **The toggles are CSS-only radio groups** (spec §2.6): the radios are the first children of the section (`#lvl-c|t|a`, `#env-0…`) or of `.pp-alts` (`#alt-0…`), so `:checked ~ *` reaches everything after them; values carry `q l-c` (by level) or `qe l-c e-0` (by level and environment), env-only chips `eo e-0`, refused ones `pref e-0`. Environments and alternatives are numbered, not named, so `plugin-page.css` writes the rules for `ENV_TOGGLE_MAX` (6) environments and four alternatives (`CREDENTIAL_ALTERNATIVES_MAX`); a test fails if a plugin's toggle would need more. Every state is in the HTML: a reader without CSS sees all of them.
- **The references import packages, never the app**: `@vaubaan/gateway-core` (the refusal builders) is a dependency like `@vaubaan/policy-engine`; the agent bootstrap (`apps/gateway/src/app/agent-bootstrap.md/content.md`) and the gateway spec are read as files. Its §5 tables must list exactly `REFUSAL_CODES` and `AUTH_FAILURE_REASONS`, and `PERSON_NEXT` is keyed by code: a new refusal code fails the build until both have its line. The examples in `concepts/permissions.mdx` are real permission ids in their real rows, and its trust-level lines quote `TRUST_LEVEL_HINTS` (`sources-agree.test.ts`).
- **What the site cannot import, it restates and tests**: the cardinality words and the three environment rules are the gateway reference's (`apps/gateway/src/lib/services/reference.ts`); `sources-agree.test.ts` reads that file and fails when they differ. The resource entity is not declared by plugins: `isResourceEntity` derives it from `resourceNoun` (same word, last word, `-`-joined words, or the entity a one-word noun starts with: `repo` for "repository"); a test fails when a plugin with a noun gets no entity. The Account / Resource / Environment callouts cut the plugin's `summary` (`summaryParts`: the first clause, the sentences naming an environment, the rest).
- **The shared sheet declares no colour, size or space**: every value is a `--pp-*` property, and the site maps them to its own tokens on `.plugin-page` at the end of `globals.css` (`service-page.test.tsx` refuses a raw colour and an unscoped rule; every rule sits under `.plugin-page`). **Colours are the shared tokens, light and dark, AA**: `globals.css` writes none (`trace-identity.test.tsx` refuses a raw colour and a token outside `CONTRAST_PAIRS`, hairlines aside); the four rows take `--row-N-{bg,fg,border}` (light pills, no glyph: the word carries the order), "ask me" the approval family (the accent), "no" the refused red, "yes" the allowed green, the environment and the connect guide's path neutral and accent-soft. A service mark keeps its brand colour (`--mark-color`); in the dark theme a near-black one takes the ink (`--mark-color-dark`), by `serviceMarkColors` of `@vaubaan/shared/service-mark` — the gateway's own rule, imported, not restated.
- **The service mark is drawn where a service is named in HTML**: the header of `/plugins/<id>` and each link of `/plugins` (`pluginListComponents`, `components/plugin/PluginListLink.tsx`, handed to `GeneratedPage` as Markdown renderers). The Markdown twin and the generated MDX stay plain Markdown, without the icon; the former per-service doc pages are redirects, so there is no other place to draw it.
- **Every page has a Markdown twin** (`/index.md`, `/docs/….md`), listed in `llms.txt`; the proxy serves the twin when `Accept` ranks `text/markdown` above `text/html`. A product page's twin carries both projects' texts, labelled, and its drawings as images with their text alternative.
- **The project switch works without script** (spec §2.1): two radios (`#project-dev`, `#project-consultant`) and three rules at the end of `globals.css` that show a `[data-project]` block while its radio is checked (`:root:has(...)`). The one script of the site is the switch's own, inline after the radios: it restores the choice kept in `localStorage` (`vaubaan-project`) before the page paints and keeps the next one, every access in `try`; `/consultants` (`data-forced`) ignores the kept choice. A drawing is a `<picture>` per project, `prefers-color-scheme` choosing light or dark, the hidden one lazy and never loaded.
- **Every claim of the landing and the product pages is true today** (spec §2.1): a planned thing carries its status beside it (`status: 'planned'`, `TODAY_STEPS`), never a button; `product-pages.test.ts` refuses a download. The README opens with `PROMISE` and `LANDING_LEDE`, character for character (same test).
- **The drawings are drawn from the catalogs as they are**: `drawings.test.ts` fails when `facts.json` differs from the catalogs, when `prims.py` holds a colour that is not a token's, or when a drawing shows what is not built. A catalog change of GitHub, Supabase, Gmail, Notion or Google Calendar can therefore fail the site's tests: regenerate (Procedure).
- **Health is never invented, and never gated**: the site reads two aggregates in parallel, `/v1/plugin_stats?tool=is.null` (calls, successes, rejected credentials, rate, `validated`) and `/v1/plugin_instances` (distinct gateways per version, minor and plugin). Each that fails, or is skipped (`VAUBAAN_SITE_OFFLINE=1`), turns its own figures into "not read" (`null` in `plugins.json`, with `health_read` saying which). Every version with data shows its figures; `validated` is a word when true, never a threshold on the display. `healthOf()` is the one place that decides; it is pure and takes a snapshot.
- **A minor's gateways come from the collector, never from a sum**: `plugin_instances` groups by minor in SQL so a gateway that moved 4.0.1 → 4.0.2 counts once. Calls and the rate of a minor are sums of its versions' rows (rate = successes / (reports − rejected credentials)).
- **The footnote** (`healthFootnote()`) is on `/plugins`, `/plugins/<id>` and `/plugins/health`, and in `plugins.json`: calls over the window from instances sharing plugin health; gateways among those also sharing usage statistics, a lower bound; rejected credentials left out of the rate.
- **Health is read when a page is served, once an hour for the whole site**: every route that imports `src/site/live.ts` exports `revalidate = 3600` (`live.test.ts` keeps the literal equal to `HEALTH_REVALIDATE_SECONDS`), and the collector fetch sits in the Next.js data cache for the same hour. What repeats a plugin page (its twin, `plugins.json`, `llms-full.txt`) is rendered by the same functions, so it shows the same figures.

- **The versions feed's data are committed files, not pages** ([ADR](../decisions/plugins-bundled-or-pinned-by-the-operator.md)): `src/content/releases.json` (`{ gateway, prerelease, date, plugins: { <id>: <version> } }`) is written by `npm run release:prepare` — at a gateway release from the root and every `plugins/*/package.json` but `_template`, at a plugin hotfix (`-- --plugin <id>`) that plugin's entry alone; never edited by hand. `src/content/advisories.json` is a JSON list, hand-written in the fix's pull request, one object per advisory, the shape of `VersionsFeedAdvisory` (`@vaubaan/shared/versions-feed`, which the gateway checks): `id` (`VBN-<year>-<nnn>`), `subject` (`gateway` or `plugin:<id>`), `affected` (a semver range), `fixed` (the first fixed version), `summary` (one sentence, at most 1000 characters), `url` (https), `date` (`YYYY-MM-DD`). An advisory is never removed: a fixed one stays, its range says who is affected. `release-data.test.ts` (gateway structural tests) holds both files to the feed's guard. [`app/versions.json/route.ts`](../../apps/website/src/app/versions.json/route.ts) serves them as the feed: `force-static`, rendered once at build (`generated_at` is the build time), `Cache-Control: public, max-age=3600`; `buildVersionsFeed()` (`content/versions-feed.ts`) throws on a file `isVersionsFeed` refuses, so a malformed advisory fails the build. A changed advisory reaches the feed with the next deploy of the site, not before.

## Traps

- **A doc page the gateway links to is checked from the gateway's side**: renaming a heading or a page of `content/docs` the gateway's `DOC_PAGES` points to fails `apps/gateway/tests/unit/app/doc-links.test.ts`; move the entry with it. A generated page cannot be a target (its twin is not its own source): link a hand-written page that links on. A page turned into a folder keeps its URL as `<name>/index.mdx` (`concepts`), no redirect needed.
- **Reshaping the agent bootstrap's §5 or the spec's §0 / §0 bis breaks the site build**: the references parse them (two tables under `## 5. When a call is refused`, three columns each; the `- **word** —` list under `## 0. Vocabulary`; a two-column table under `## 0 bis. Interface words`). The table sits outside §0 on purpose: the harness reads every table row under a "Vocabulary" heading (down to the next `##`) as a term; moving it back puts its rows among the spec's terms.

- **A sample on the fallback fails the build**: `loadPlugins()` throws `ExampleError` (from `generate`, `type-check` and the unit tests alike) naming the plugin, the tool and the sample (`'<tool>' sample #n slice #m`), when a sample's slice matches no catalog entry or only the fallback (a missing entry), when `classify` refuses a sample not marked `expectDenied`, or accepts one that is. Fix the catalog or the sample in the plugin, as the plugin's coverage test would ask; never filter it out in the site.
- **Generated and gitignored** — never edit by hand: `.generated/`, `.source/`, `public/`, `content/docs/configuration/keys.mdx`, `content/docs/known-limitations.mdx`, `content/docs/reference/*.mdx` but its hand-written `index.mdx`. The generator empties `public/` and removes every file marked `generated: true` on each run. `public/` holds `llms.txt`, `sitemap.xml`, `robots.txt`, `.well-known/security.txt` (RFC 9116; its `Expires` is counted from the build, so a site not deployed for 180 days publishes an expired one) and the connect guides' screenshots (`BuiltSite.assets`: `plugins/<id>/connect/<file>`, copied from the plugin's `docs/connect/`; the internal-link test knows them) only: the Markdown twins, `plugins.json`, `llms-full.txt` and `versions.json` are routes (`LIVE_FILES`, `BUILT_ROUTE_FILES` in `outputs.ts`, which the internal-link test reads).
- **`revalidate` must be a literal** in a page or route file: Next.js reads it statically, so `export const revalidate = HEALTH_REVALIDATE_SECONDS` silently gives no caching. Write `3600` and let `live.test.ts` catch a drift.
- **`/.well-known/microsoft-identity-association.json` is a route, not a public file** (`app/.well-known/…/route.ts`, `force-dynamic`): the generator empties `public/`, and the ids are read at request time, never built in. Vercel binds variables to a deployment: after changing `MICROSOFT_IDENTITY_APP_IDS`, redeploy production (no rebuild needed), or the route keeps the former ids. No application id is written in the code.
- **`/twins/…` is reachable directly** (the proxy rewrites to it); it is not listed anywhere and serves the same text as the `.md` address.
- **`components/plugin/` imports relatively, never through `@/`**: the root `vitest.config.ts` maps `@/` to the gateway's `src`, and `plugin-page.test.tsx` — and the gateway's `reference-page.test.tsx`, which compares the two renders — render `PluginPageView` with `react-dom/server`. Node code of the site (`plugin-pages.ts`, `outputs.ts`, the generator) imports the package's `/page-data` and `/info` entries, never `.`, whose React view the generator's `tsx` cannot run. Only the route file (`app/plugins/[id]/page.tsx`) uses `@/`.
- **The twin does not link to itself**: `pluginLinks()` ends with the `.md` address for the HTML page; the twin names `/plugins/<id>` instead (the internal-link test of `site.test.ts` knows pages, not twins).
- **Hand-written docs are plain Markdown in `.mdx`**: `loadHandwrittenDocs()` refuses an `import`/`export` line, a `<Tag` or a `{` outside code (write `your-domain` in prose, `<your domain>` in a code span).
- **Plugin strings go through `text()`**, which escapes Markdown. The plugins' README "Credential" sections are no longer read: the connect guide is section 9 of `/plugins/<id>` (`#connect`), from the declaration alone.
- **`/docs/providers/<id>` is a redirect, not a page** (`src/site/redirects.ts`, read by `next.config.ts`; the `.md` address goes to the plugin page's twin), and so is the former index `/docs/providers` (and its `.md`), which answers at `/docs/services` since the rename R2 (ADR one-word-per-thing-account-service-plugin; `redirects.test.ts`). The index `/docs/services` is a hand-written page; never put a page under a redirected path. `/docs/install-with-your-coding-agent` (and its `.md`) answers at `/docs/install/with-your-coding-agent` the same way. A page that moves keeps a redirect pair (HTML and `.md` twin) in `SITE_REDIRECTS` and a case in `redirects.test.ts`. A link to a service's guide is `connectGuidePath(id)`.
- **A screenshot's words are derived, never written**: the provenance line is `screenshotAttribution` of the SDK, the same the gateway prints; the licence words travel in `ConnectFigureInfo.licenceWords` so that the page code imports nothing of the SDK at run time (the SDK is a devDependency, not transpiled). The credits line at the foot of `/plugins` lists each documentation and licence once, nothing when no page shows one.
- **Without `COLLECTOR_HOST`** every host is the site's and the collector routes refuse by themselves; with it, that host answers only `/v1/…` and a `Disallow: /` robots file.
- **No theme toggle on purpose**: dark follows `prefers-color-scheme` through the tokens' own media block (and the drawings' `<picture>`). **Never write a `dark:` utility**: Tailwind's `dark` variant matches `.dark` or `[data-theme='dark']` only, which the site never sets (a test refuses it in `globals.css`).
- **Tailwind's preflight removes the browser's defaults** (heading sizes, list markers, margins): Markdown and MDX render plain elements without classes, so `.prose` in `globals.css` gives them back; the plugin page's shared sheet was written over the defaults, so its lists get `list-style`/`padding-left: revert` (in the base layer, which the unlayered shared sheet overrides where it sets its own). A new element in hand-written MDX (a `<dl>`, an image) may need a `.prose` rule.
- **Fonts are Geist through `geist/font`** (`layout.tsx`, the classes on `<html>` set `--font-geist-sans`/`-mono`, which the tokens read): self-hosted under `/_next/static/media`, nothing from a third party. The site's mono is `--site-mono`, handed to the plugin page as `--pp-font-mono`.
- **The mark, favicon and social card**: `components/Lockup.tsx` (inline, `currentColor`), `app/icon.svg` (adapts to the scheme), `app/apple-icon.png` (180) and `app/opengraph-image.png` (1200×630, alt text beside it) are Next's file conventions, not `public/` (which the generator empties). The PNGs are renders of the SVG sources in `apps/website/brand/` (the social card set in Geist): re-render them with a headless Chromium at their size when a source changes.
- **A `[data-project]` element takes no display utility**: the switch's rules are unlayered, so `display: none` and `display: revert` override it; wrap the flex or grid inside.
- **A new product page** is four places: its entry in `PRODUCT_PAGES` (or `build-site.ts` for a page of its own), its route under `app/`, its path in `TWINNED` (`site/routing.ts`) and in the `Vary` source of `next.config.ts`; `site.test.ts` lists the pages it expects.
- **A drawing's text that names a permission comes from `SHORT`**: a permission added to one of the five catalogs stops `gen.py` (`no short name for …`) until it has one.
- **Vercel builds only when the site's inputs change** since the last deployed commit: `vercel.json` `ignoreCommand` runs [`scripts/vercel-ignore.sh`](../../apps/website/scripts/vercel-ignore.sh), whose path list must name every input the generator reads (a new package the site imports goes there too). Vercel refuses a `vercel.json` whose `ignoreCommand` is longer than 256 characters: the whole deployment fails at schema validation, before any build.

## Outside the repo — Vercel project

- Root `apps/website`, Node 22, framework Next.js, build `npm run build`, and **"Include files outside the root directory in the Build Step" on**: the generator reads `plugins/`, `docs/`, `deploy/` and workspace packages.
- Request-time variables: `COLLECTOR_HOST`, `COLLECTOR_SUPABASE_URL`, `COLLECTOR_SUPABASE_PUBLISHABLE_KEY`, and `MICROSOFT_IDENTITY_APP_IDS` (comma-separated Entra application ids; `/.well-known/microsoft-identity-association.json` answers Microsoft's publisher-domain check from it, 404 without it: the OAuth broker's `microsoft` client names vaubaan.com as its publisher domain, [oauth-broker-contract](oauth-broker-contract.md)); the build needs none. No log drain, no Observability Plus, no analytics.
- The pages under `/plugins` and the twins route run as functions once an hour (ISR); nothing to configure, Vercel's defaults carry it.

## Procedure — regenerate the drawings

From the repository root, Python 3 (standard library only):

```bash
npx tsx apps/website/scripts/drawing-facts.ts   # facts.json, from the catalogs
python3 apps/website/drawings/gen.py            # svg/*.svg and svg/drawings.json
```

Check a few renders in both themes (a browser opening the SVG is enough), commit `facts.json` and `svg/` with the change. A scene's words that a catalog change makes false stop `gen.py` on an `assert`: redraw the scene, never delete the assert.

## Debug

- **`site.json is missing`** → `npm run generate --workspace @vaubaan/website`.
- **"not plain Markdown"** → a `<`, `{` or component in prose: use a code span.
- **"the refusal codes table differs from the gateway's"** → a code was added or renamed: add its row to §5 of the agent bootstrap and its line to `PERSON_NEXT` (`references.ts`), with an example in `EXAMPLES`.
- **MDX error in a generated page** → `escapeMdx()` missed a construct: add it to `markdown.ts` and `units.test.ts`.
- **Every plugin reads "not read"** → the collector did not answer within 4 s when the page was last rendered (`https://telemetry.vaubaan.com/v1/plugin_stats?tool=is.null`, `…/v1/plugin_instances`); the next render, within the hour, tries again. `/plugins/health` names the time of the last successful read.
- **Gateways "not read", calls fine** → `plugin_instances` is missing on the collector's store: apply `deploy/collector/schema.sql`.
- **A new release's minor reads "no call yet"** while the previous one had hundreds → expected: the list's second row keeps the previous minor; the plugin page lists the last ten versions.
