# Embedded store — SQLite via better-sqlite3, in-house forward-only migrations

> Fixes what the pivot ADR [[pivot-v4-to-v5-on-prem-mission-tokens]] (D1: SQLite on a
> mounted volume) left open: the driver, the migration tooling, the schema conventions,
> the durability trade-off, the audit immutability mechanism and the backup story.
> Implemented by feature P0.3 of the v5 plan. Handbook: [store](../handbook/store.md).

## Context

v5 is a single-company, single-process gateway shipped as one Docker image. D1 of the
pivot ADR chose SQLite on a mounted volume to remove every external service. What D1
does not say:

- **Driver.** Two credible options in 2026: `better-sqlite3` (mature synchronous
  binding, prebuilt native binaries, `transaction().immediate()`), or Node's built-in
  `node:sqlite` (`DatabaseSync`, no native dependency). The repository's `engines`
  field allows Node 20; `node:sqlite` does not exist there, is still marked
  experimental on Node 22 (it prints a warning at load), and typing it requires an
  `@types/node` bump outside the store's perimeter.
- **Migrations.** The 42 Supabase migrations of v4 were applied by the Supabase CLI
  from CI. v5 has no CI access to the operator's database: the schema must be owned by
  the application and applied at boot.
- **Scaling clause.** The common rules for v5 require that nothing preclude a hosted
  or horizontally scaled deployment later: repositories behind interfaces, SQL
  portable to Postgres, every SQLite-only construct identified.
- **Invariants the schema must carry structurally**, not by convention: enumerations
  of `RiskId` are rows (no JSON array can hide a wildcard); the audit is immutable
  (spec §6); the budget decision and its decrement are one atomic operation (spec §6,
  "authoritative, atomic counting").
- **Durability.** Spec §3.3: a restart must never forget a consumed credit; the plan
  (§3.5) accepts losing a few seconds of in-memory rate-limit state, not a quota.

## Decision

### Driver: `better-sqlite3` 12.x, pinned, synchronous

- `better-sqlite3@12.11.1` (exact) with `@types/better-sqlite3`. The 12.x line covers
  Node 20 through 26, so it honours `engines.node >= 20`; 13.x would force Node 22.
  Re-evaluate `node:sqlite` when it reaches stability 2 on the Node LTS the image uses.
- The driver is referenced in exactly one module, `apps/gateway/src/server/store/db.ts`.
  Repositories receive the handle and speak SQL; a Postgres adapter replaces `db.ts`
  and the few spots listed under "Portability" below.
- Repository interfaces are **asynchronous** (`Promise`-returning) even though the
  SQLite implementation is synchronous underneath. This costs a microtask per call and
  keeps the interfaces implementable over a network driver later. Code that must run
  inside a transaction (the `decide` callback) stays synchronous by contract.

### Migrations: in-house forward-only runner over numbered `.sql` files

- Files `apps/gateway/migrations/NNNN_name.sql`, applied in order at boot by
  `runMigrations()`; each file runs in one `BEGIN IMMEDIATE` transaction and is recorded
  in `schema_migrations(version, name, checksum, applied_at)`. Re-running is a no-op.
- Applied migrations are **immutable**: a checksum mismatch aborts the boot. A fix is a
  new file. No down migrations.
- The runner creates `schema_migrations` itself (`CREATE TABLE IF NOT EXISTS`) so the
  first migration can be ordinary DDL.
- About 120 lines, zero dependency. Drizzle/Kysely were rejected (below).

### Schema conventions

- **Ids**: `TEXT` UUIDv7 (RFC 9562), generated by the application. Time-ordered for
  append-mostly tables (`audit`, `events`), unguessable, and `uuidv7()` is native in
  Postgres 18 for the port. The generator is monotonic within one process (RFC 9562
  §6.2 method 1, a 12-bit counter in `rand_a`), so `ORDER BY ts, id` is insertion order
  for rows the process wrote even when a clock tick or a frozen test clock gives two
  rows the same timestamp. Ordering between two processes in the same millisecond is
  not guaranteed and nothing relies on it (`// single-process only` in `ids.ts`).
- **Timestamps**: ISO-8601 UTC `TEXT` (`2026-10-13T09:00:00.000Z`), always produced by
  the application through a `Clock` interface. Lexicographically sortable, readable
  in the `sqlite3` shell, maps to `timestamptz` on Postgres. `CURRENT_TIMESTAMP` is
  never used because its format differs between engines; tests inject a manual clock.
- **`STRICT` tables** everywhere (SQLite ≥ 3.37, checked at open): column types are
  enforced, so a quota can never be stored as text.
- **Enumerations are rows**: `share_restrictions(share_id, risk_id)`,
  `mission_policy(mission_id, risk_id, quota, rate_limit, rate_window_seconds, gate)`,
  `audit_risks(audit_id, risk_id, accepted, touched, remaining)` _(changed
  2026-10-23 by [audit-risk-snapshot-stored-once](./audit-risk-snapshot-stored-once.md):
  the touched risks only, the accepted snapshot in `audit_risk_set_members`, once
  per distinct set)_. A `CHECK` on
  `risk_id` forbids the empty string and the `*` character, and the repositories check
  every `risk_id` against the loaded catalog (`CatalogIndex`) before writing. The
  "never a sentinel" structural test is therefore a `SELECT … WHERE risk_id NOT IN
catalog` and an insert attempt.
- **Polymorphic principals** (owner of a connection, target of a share) use a
  `*_kind` column plus two nullable foreign keys (`*_user_id`, `*_group_id`) and a
  `CHECK` that exactly the matching one is set, so referential integrity holds on
  both sides.
- **Encrypted blobs**: `BLOB` AEAD output plus a `key_version INTEGER` column, with
  the row id as associated data (`connections.credential_blob` ← connection id;
  `requests.args_blob` ← `request:<id>`; `instance_config.secret_blob` ←
  `instance_config:<key>`). The store depends on the `Encryptor` port of the crypto
  module (P0.4, `apps/gateway/src/server/crypto/encryptor.ts`): `encrypt(id, text)` →
  `{ keyVersion, blob }`, `decrypt(id, { keyVersion, blob })`. That port is
  asynchronous while better-sqlite3 transactions are synchronous, so repositories
  seal **before** opening a transaction and open **after** it; an approval request
  dropped from inside the decision transaction receives arguments sealed ahead of
  time by `RequestsRepo.prepareArguments()`, which fixes the request id (the
  associated data) first.
- **JSON `TEXT`** is allowed only for opaque metadata (`connections.metadata_json`)
  and forensic snapshots never read for authorization (`audit.slices_json`,
  `events.details_json`, `requests.decision_json`).

### Pragmas and durability

`journal_mode = WAL`, `synchronous = NORMAL`, `foreign_keys = ON`, `busy_timeout` 5 s.
In WAL mode `NORMAL` survives a process crash with every committed transaction intact
and loses at most the last transactions on an OS crash or power loss, never
consistency. A gateway on a company server with a UPS-backed volume gets this
trade-off; an operator who wants `FULL` can set it in a later configuration key
without a schema change.

### Audit immutability by triggers, purge through one window

`BEFORE UPDATE` triggers on `audit` and `audit_risks` always `RAISE(ABORT)`. `BEFORE
DELETE` triggers abort unless the single-row table `audit_purge_guard` holds a cutoff
newer than the row. `AuditRepo.purgeOlderThan(cutoff)` inserts that row, deletes
`audit_risks` then `audit` older than the cutoff, and removes the row, all in one
transaction. Any other delete, including a delete of a recent row during a purge,
aborts. Retention defaults to 90 days (spec §8) and is a repository parameter the
operator configures.

Consequence for the hot path: an audit row is written **once**, after the upstream
call, with the decision and the latency together. The decision itself is made
durable before the upstream call by the `events` row written inside the decision
transaction. Plan §3.5 sketched "audit(pending) … then update latency"; the spec's
"no update from the application" wins.

### Atomic decision primitive

`SessionsRepo.decideAndDecrement(input, decide)` runs inside `BEGIN IMMEDIATE`: get or
create the session, read the counters of the touched risks for the period, call the
synchronous `decide` callback (which may consume an approval, drop a request and
record events through the context it receives), then increment every touched counter
by one when the outcome allows, and commit. Counters are durable rows
(`session_counters(session_id, risk_id, period_start, consumed)`, UPSERT on increment).
The accounting rules themselves (period arithmetic, quota and rate comparison, gate
handling) are P1.3's `decide` callback.

### Backup

`Store.backupTo(path)` runs `VACUUM INTO ?`: a consistent, compacted single-file copy
taken while the gateway runs, with no `-wal` sidecar to pair. The operator schedules it
(cron on the host, or a later admin action) and ships the copy wherever company
backups go. A raw volume snapshot is also valid **only** if it captures the main file
and its `-wal` file atomically, which most block-level snapshots do and most file
copies do not; the handbook says so.

### Portability notes for a future Postgres adapter

Everything is standard SQL except the following, each marked `-- sqlite:` in
`0001_schema.sql` or isolated in `db.ts`:

| SQLite-only construct                          | Postgres replacement                                  |
| ---------------------------------------------- | ----------------------------------------------------- |
| `STRICT` table option                          | drop the keyword (Postgres types are strict)          |
| `SELECT RAISE(ABORT, '…')` in triggers         | trigger function with `RAISE EXCEPTION`               |
| `PRAGMA journal_mode/synchronous/foreign_keys` | server configuration                                  |
| `BEGIN IMMEDIATE`                              | `BEGIN` plus `SELECT … FOR UPDATE` on the session row |
| `VACUUM INTO`                                  | `pg_dump` / base backup                               |
| `?` positional parameters                      | `$1 … $n` (driver-level rewrite)                      |

UPSERT (`ON CONFLICT … DO UPDATE SET … excluded.*`), partial unique indexes,
composite foreign keys, `CHECK` constraints and `NOT LIKE` are accepted as written.

## Consequences

- One native dependency in the image. The Docker build (P0.4) must either download
  the prebuilt binary for the image's Node/libc or compile it; both are routine, and
  `prebuild-install`'s deprecation warning is cosmetic.
- The schema lives in the repository and is applied by the process: an operator never
  runs a migration by hand, and a downgrade of the image against a newer schema fails
  fast with a named migration.
- Every repository test runs on `:memory:` with the real schema and triggers; the
  suite needs no service. The N-concurrent `decideAndDecrement` test and the
  two-handle `SQLITE_BUSY` test prove serialization where the process actually relies
  on it.
- `SqliteAuditWriter` implements `@vaubaan/gateway-core`'s `AuditWriter` (P0.5) and
  `AuditRepo.append` takes gateway-core's `AuditEntry` as is: `risks_touched`,
  `accepted_risks_snapshot` and `remaining_budget` are unfolded into `audit_risks`
  rows and folded back on read, so a record round-trips the entry. _(Changed
  2026-10-23 by [audit-risk-snapshot-stored-once](./audit-risk-snapshot-stored-once.md):
  the snapshot goes to a set stored once, the rows and the remaining budget cover
  the touched risks.)_ The entry shape
  has one owner, gateway-core; the store has no audit type of its own.
- The returned `Store` satisfies the composition root's `Store` port
  (`compose/ports.ts`: `kind`, `ping()`, `close()`), so the root can inject
  `openStore()` without an adapter. The root's `openStore(config, logger)` hook does
  not yet pass the encryptor it builds; wiring is a one-line follow-up in the root.
- `mission_policy` carries `rate_window_seconds` in addition to `rate_limit`: a rate
  "per short sliding window" is meaningless without the window length, and the
  catalog bounds it per risk.
- Missions carry `mission_connections(resource_scope: all|selected)` plus
  `mission_resources` rows: "all of the connection's resources by default" (spec
  §0) is a scope value, not an enumeration that would freeze at issuance.

## Rejected alternatives

- **`node:sqlite` (built-in).** No native dependency and a smaller image, but absent
  on Node 20, experimental on Node 22 (runtime warning), no transaction helper, and
  its types require an `@types/node` major bump. Revisit when stable on the image's
  Node LTS; the change is confined to `db.ts`.
- **Drizzle or Kysely migrations and query builder.** Typed queries are attractive,
  but the migration half adds a code generator, a second schema description that
  drifts from the SQL, and a dependency surface for a schema a human must still read
  in the `sqlite3` shell during an incident. Hand-written SQL behind repositories is
  smaller and the portability is explicit rather than delegated to a dialect layer.
- **Audit immutability by convention** (no triggers, "the app never updates"). The v4
  `audit_log` relied on this and on RLS. In a single-process store the trigger is the
  only thing standing between an operator's ad-hoc `UPDATE` and the record; the plan
  asked for structural enforcement.
- **Allowing a write-once `upstream_latency_ms` update.** Would implement plan §3.5
  literally with an `UPDATE OF upstream_latency_ms … WHEN OLD IS NULL` exception. It
  weakens "no update" for one field and complicates the Postgres port; writing the
  audit row once after the upstream call, with the `events` row as the durable
  pre-commitment, keeps the spec's wording intact.
- **ULID ids.** Equivalent ordering properties, but no native type or generator on
  the Postgres side and a second encoding (Crockford base32) to explain.
- **Epoch-millisecond `INTEGER` timestamps.** Faster comparisons, but opaque in the
  shell and a second conversion at every boundary; the audit is read by humans
  during incidents.
- **`synchronous = FULL`.** Safer on power loss at the cost of an `fsync` per
  transaction on the hot path; the plan's trade-off (lose seconds of rate-limit
  state, never a quota) is met by `NORMAL` in WAL mode for the failure modes a
  process controls. Left as a future configuration key.
- **Deleting audit rows by dropping and recreating the trigger.** Works, but a crash
  between the drop and the recreate leaves the table unprotected; the guard row is
  inside the same transaction as the delete and cannot outlive it.
- **JSON arrays for `risks_touched` and the accepted-risks snapshot in the audit**,
  as v4 did. Rows keep the counters-vs-audit structural check a plain join on both
  engines and apply the "enumerations are rows" rule uniformly.
